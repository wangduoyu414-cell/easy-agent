# Hermes 固定源码安装模式：待决设计

状态：方案与验收条件已整理，尚未实现或启用。新增分发方式的用户选择仍待确认；现有官方安装器路线和禁用条件不变。

依据：[M1 固定源码真实运行证据](../evidence/hermes-fixed-source-runtime-2026-09-06.md)。该实验已证明固定源码可构建、桌面可认证连接同机后端；未证明默认 local bootstrap、升级或修复可用。

## 来源合同

本地版本化清单分别记录官方仓库 URL、完整 commit、构建范围、desktop/runtime 版本、工具链版本、锁文件摘要和 Electron 制品摘要。Release 标签只作显示，不把标签或 main 的当前指向当成固定版本。

当前实验使用 v2026.8.31 的 commit `29112bef099274229cadff79cdff7bf7b99c4b77`，desktop 0.17.0、runtime 0.21.0。setup 0.0.1 不参与源码模式的安装成功判定。清单必须明确本地构建来源；ad-hoc 签名不能标记为官方发布者验证通过。

源码获取需完整验证声明的构建范围。生产实现不能依赖实验缓存中的 Git alternates，也不能把截断归档当成完整下载。优先完整官方归档与固定摘要；若采用 Git 对象验证，必须校验 commit/tree/blob 的完整关联并明确排除目录。解包前拒绝路径逃逸、危险链接、重复路径和大小写冲突，限定文件数量与解压总量；不静默覆盖冲突文件。

Node、uv、Python、Electron 和原生构建工具需要独立的固定版本、官方来源及完整性合同，不能依赖宿主 PATH 恰好可用。npm 仅按锁文件安装；Python 仅按锁文件同步。锁定失败直接报告失败，不转 npm install、重新解析 PyPI 或第三方镜像。首次依赖脚本默认不执行；必要的构建脚本及其联网行为需要明确列出并纳入验证。

## 安装状态与数据归属

建议状态序列：预检 → 获取 → 验证 → 构建暂存 → 验证桌面 → 验证后端 → 验证认证连接 → 激活 → 复检。每一步保存结构化结果，不能用 bootstrap 退出码或 health 200 单独宣布成功。

版本化构建目录与用户数据目录分离。暂存版本通过验证后才可激活，旧可用版本在此之前保持可用。失败只清理本次明确拥有的暂存目录和子进程；不递归清理已有 `~/.hermes`，不按进程名终止其他 Hermes 实例。进程归属记录需包含 PID、启动时间和实际可执行路径，避免 PID 复用。

源码模式不自动运行上游跟随 main 的更新/修复脚本。更新必须重新经过同一套固定清单流程。已有用户数据的迁移与恢复规则尚未验证，因此首个实现应拒绝自动迁移未知旧安装；数据迁移失败也不能仅通过切回旧二进制宣称恢复成功。

固定 commit 的 `apps/desktop/electron/main.ts` 还存在需要处理的运行期入口：找不到可用后端会调用 `runBootstrap`；解析器可能采用 PATH 上的 Hermes 或系统 Python 中的 `hermes_cli`；renderer 请求修复时，`bootstrap-repair-guard.ts` 默认允许三次软重启，后续升级为硬重装。因此，即使首次安装固定成功，后续启动和修复仍可能离开受管理版本。必须验证这些分支的实际约束，不能仅靠安装时传入 commit 宣称后续一直固定。此结论来自上述 commit 源码审查，尚未进行故障注入实测。

取消需要按阶段定义：下载可立即终止并丢弃未验证文件；构建终止本次进程树并等待退出；激活阶段完成一个明确的文件切换边界后再响应。崩溃重启只读取日志、检查暂存残留和重新扫描，不自动继续执行未完成脚本。

## 桌面与后端验收

| 检查 | 成功要求 | 已有证据 |
| --- | --- | --- |
| 源码与依赖 | 固定清单和实际文件相符，锁定失败不降级 | 实验构建范围已核验，生产获取流程待实现 |
| 桌面身份 | 正确 Bundle ID、ARM64、主程序、独立 desktop 版本及签名完整性 | 实际自建样本通过；不是厂商签名 |
| 后端存活 | 自有 PID、Python、工作目录、回环监听和 runtime 版本一致 | 实际后端通过 |
| 认证连接 | 桌面能读取受保护的 profiles API；令牌仅用于自有实例 | remote 模式连接同机后端通过 |
| 默认启动 | 从受管理入口冷启动、退出、再次启动均正确归属 | 待验证，不能沿用 remote 实验结论 |
| 模型能力 | 只有用户配置并授权模型访问后才验证 | 未测试，不作为无凭据安装的默认承诺 |
| 激活与恢复 | 失败/取消/崩溃后旧版本和数据状态明确 | 待实现与故障注入验证 |

进程绑定 health 探针是诊断快照，不是认证机制。正式复检还应完成认证后的最小只读 API 调用；不能把会话令牌写入命令行、日志或长期保存的证据。前端和后端的配置归属需要按官方生命周期行为验证，不能仅凭临时目录不同就假设隔离成立。

## 关联影响与交付顺序

此模式新增依赖下载、构建耗时、磁盘预算、取消和版本管理职责，需要独立 executor 与 postcheck，不能塞入 DirectAppBundle 或放宽通用签名策略。WorkBuddy 的窄范围兼容和其他四产品流程应保持独立。

第一步只实现 Apple Silicon 的固定清单解析、下载验证和暂存构建；第二步补齐默认启动、认证连接及退出；第三步验证激活、取消、崩溃和旧数据兼容。完成这些证据后才讨论启用 GUI 安装。Intel 和 Windows 必须各自取得工具链、原生依赖、文件系统及真实启动证据，不能由 M1 成功推导支持。

如果继续保持官方安装器路线，下一项可解除阻塞的证据是厂商可验证的固定版本 bootstrap（含锁定的下游行为），或完整签名桌面/runtime 分发物。仅官网版本稳定、setup 签名有效或源码构建成功，都不足以单独启用当前 Mac 安装入口。
